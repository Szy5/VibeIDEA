# 推荐论文批量解析与先前工作提取交接文档

## 1. 目标

这部分工作的目标，是把筛选出的 ACL/AAAI 推荐论文批量处理成 Sci-Reasoning 风格的 prior work analysis 结果，核心要求有三点：

1. 输入不是 arXiv 搜索结果，而是本项目本地推荐出的论文 JSONL。
2. 输出仍然沿用 Sci-Reasoning 原始目标，不改 prior work 提取提示词和报告意图。
3. 每篇论文需要同时产出结构化 JSON 和 Markdown 报告，并把原始 PDF 下载到 `raw_paper` 目录下。

当前实现代码在：

- [backend/summarize_recommended_papers.py](/home/sunzongyuan/projects/VibeIDEA/VibeIDEA/backend/summarize_recommended_papers.py)

相关输入输出目录：

- 推荐输入 JSONL: [raw_paper/recommended_acl_aaai_top300_min7.65.jsonl](/home/sunzongyuan/projects/VibeIDEA/VibeIDEA/raw_paper/recommended_acl_aaai_top300_min7.65.jsonl)
- PDF 下载目录: [raw_paper/pdfs](/home/sunzongyuan/projects/VibeIDEA/VibeIDEA/raw_paper/pdfs)
- prior work 输出目录: [results/recommended_acl_aaai_top300_min7.65_prior_work](/home/sunzongyuan/projects/VibeIDEA/VibeIDEA/results/recommended_acl_aaai_top300_min7.65_prior_work)
- 下载清单: [results/recommended_acl_aaai_top300_min7.65_prior_work_download_manifest.json](/home/sunzongyuan/projects/VibeIDEA/VibeIDEA/results/recommended_acl_aaai_top300_min7.65_prior_work_download_manifest.json)

## 2. 当前实现范围

### 2.1 输入格式

脚本读取本地推荐结果 JSONL，每一行至少包含：

- `title`
- `summary`
- `abstract`
- `authors`
- `venue`
- `year`
- `url`

可选字段：

- `doi`
- `arxiv_id`

对应加载逻辑在 `RecommendedPaper` 和 `load_recommended_papers()` 中。

### 2.2 PDF 获取逻辑

PDF 获取逻辑不再依赖 Sci-Reasoning 原始的 arXiv 元信息链路，而是改为根据本地推荐论文的 `url` 推导官方 PDF 地址。

核心函数：

- `infer_arxiv_id()`
- `resolve_pdf_url()`
- `get_pdf_storage_path()`
- `ensure_pdf_downloaded()`

支持的来源：

1. arXiv
2. ACL Anthology
3. AAAI OJS

其中 AAAI 做过单独修复，处理顺序是：

1. 读取 `citation_pdf_url` meta tag
2. 匹配 `/article/download/...`
3. 将 `/article/view/<submission>/<galley>` 转换成 `/article/download/<submission>/<galley>`
4. 最后再从页面 HTML 里兜底推断

这个修复是为了解决 AAAI 论文 PDF 地址不稳定、直接下载失败的问题。当前 `LightPROF` 之类 AAAI 论文已经验证可下载。

### 2.3 文本抽取逻辑

PDF 文本抽取优先使用 `PyMuPDF`，失败时退回 `pdftotext`：

- `extract_pdf_text()`

处理策略：

- 默认最多抽取前 15 页
- 最多保留约 8000 个词
- 如果 PDF 抽取失败，则退化为只基于标题和摘要做 prior work 提取

### 2.4 GPT 调用逻辑

核心函数：

- `call_gpt5()`
- `analyze_prior_works()`

虽然函数名叫 `call_gpt5()`，但实际模型通过 `--model_name` 控制，不局限于 `gpt-5`。

关键点：

1. 保留了 Sci-Reasoning 原始 prior work extraction 的任务定义和输出结构。
2. 不应随意改动 `system_prompt` 和 `user_prompt`，否则输出格式和目标会偏离原项目。
3. API 从 `.env` 读取：
   - `OPENAI_API_KEY`
   - `OPENAI_API_BASE`

### 2.5 输出逻辑

每篇论文会产出两个文件：

1. `prior_work_analysis_<paper_id>.json`
2. `prior_work_analysis_<paper_id>.md`

对应逻辑：

- `process_paper()`
- `generate_markdown_report()`

批量跑完后还会生成：

- `manifest.json`

这里的 `paper_id` 优先级如下：

1. `arxiv_id`
2. `doi`
3. `slugify(title)`

因此当前输出目录里既会有按标题命名的文件，也会有按 arXiv ID 命名的文件，这是预期行为，不是异常。

## 4. 参数说明

主要参数定义在 `parse_args()` 中。

- `--input`: 推荐论文 JSONL
- `--pdf_dir`: PDF 本地存储目录
- `--output_dir`: prior work 输出目录
- `--model_name`: 调用的聊天模型名称
- `--mode`: `download | analyze | all`
- `--download_workers`: PDF 下载并发
- `--gpt_workers`: GPT 分析并发
- `--sleep_seconds`: 每篇之间额外等待时间
- `--skip_existing`: 跳过已存在 JSON 和 MD 的论文

## 5. 依赖与环境说明

### 5.1 Python 依赖

脚本依赖：

- `requests`
- `python-dotenv`
- `PyMuPDF`

注意，之前环境里出现过错误包：

- 安装了 `fitz 0.0.1.dev2`

这会导致：

- `ModuleNotFoundError: No module named 'frontend'`

正确修复方式：

```bash
python -m pip uninstall -y fitz
python -m pip install -U PyMuPDF
```

### 5.2 GPT API 环境变量

需要在 `.env` 中配置：

- `OPENAI_API_KEY`
- `OPENAI_API_BASE`

说明：

1. 之前某些代理/中转地址不支持 `gpt-5` 或 `gpt-5.1`，会返回 `model_not_found` 或 `503`。
2. `gpt-4o-mini` 曾验证可用。
3. 切换 API base/key 后，`gpt-5` 的最小调用测试也曾验证通过，但批量时仍建议先小并发测试。

## 6. 当前已知问题

### 6.1 GPT 接口稳定性

即使 API key/base 在单次测试中可用，批量多线程跑时仍可能出现：

- 卡住
- 超时
- 某些请求返回非 200

建议：

1. 先从 `--gpt_workers 3` 开始压测
2. 稳定后再提高到 `10`
3. 如果后续继续维护，优先补重试、退避和失败任务重跑机制

### 6.2 Markdown 模板与 Sci-Reasoning 不完全一致

当前 `generate_markdown_report()` 生成的 Markdown 报告是本项目内实现的稳定格式，不是直接复用 Sci-Reasoning 原始 md writer。

但 prior work 提取的核心 prompt 目标已保持一致。

如果后续要求“输出文件格式也必须字节级贴近原项目”，需要继续对齐：

1. 原项目 JSON schema
2. 原项目 Markdown 渲染模板
3. 原项目命名规则

### 6.3 输出命名不统一

由于 `paper_identifier()` 的优先级是 `arxiv_id > doi > title slug`，当前目录里混合存在：

- `prior_work_analysis_2302_11799.json`
- `prior_work_analysis_KG_Agent_An_Efficient_Autonomous_Agent_Framework_for_Complex_Reasoning_over_Knowledge_Graph.json`

这不会影响使用，但后续如果要统一命名策略，建议先做一轮元信息校准，再决定是否重命名。

## 7. 后续建议

### 7.1 优先补重试机制

建议在 `call_gpt5()` 外层增加：

1. 超时重试
2. 429/5xx 指数退避
3. 失败样本单独写入错误清单

### 7.2 把分析和下载彻底拆成两个阶段

虽然当前 `--mode` 已支持拆阶段，但后续可以进一步固化成：

1. `download_manifest.json`
2. `analysis_manifest.json`
3. `failed_cases.jsonl`

这样更适合大批量断点续跑。

### 7.3 与元信息校准脚本联动

prior work 提取完成后，建议紧接着执行标题/arXiv ID 校准脚本：

- [backend/enrich_prior_work_analysis.py](/home/sunzongyuan/projects/VibeIDEA/VibeIDEA/backend/enrich_prior_work_analysis.py)

这样可以把模型生成的 prior works 标题回填为更标准的标题，并尽量补齐 arXiv ID。

## 8. 快速接手建议

新接手的人建议按下面顺序理解代码：

1. 先看 `RecommendedPaper`、`PriorWork`、`PriorWorkAnalysis`
2. 再看 `resolve_pdf_url()`，理解 PDF 来源适配
3. 再看 `analyze_prior_works()`，理解为什么不能随便改 prompt
4. 最后看 `process_paper()` 和 `main()`，理解批处理入口

如果要继续推进，优先做的不是重写 prompt，而是增强：

1. 下载稳定性
2. GPT 调用稳定性
3. 输出结果元信息校准
